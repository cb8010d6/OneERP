# 受控试运行交付

本轮把当前源代码的容器构建、业务验收与隔离恢复接到同一个 CI 门禁。交付状态以对应 PR 精确 head 的运行记录为准；本文件不是生产上线批准。

## 验收入口

GitHub Actions 的 `CI / container-rehearsal` 从 PR head 构建现有 API production、API builder（迁移）和 Web production Docker target。所有服务及恢复副本都使用随机的 `oneerp-ci-*` 项目和临时凭据；端口只绑定 runner 的 loopback。

执行顺序：构建镜像 → 初始化空数据库 → 启动 API/Web → 检查登录页、静态资源和 API 代理 → 13 步库存贸易与 12 步制造 HTTP 链路 → 备份 PostgreSQL/MinIO → 在新卷中恢复并验证。恢复复用正在运行的镜像 ID，不重新执行管理员初始化，不覆盖源数据。

下载该次运行的 `container-rehearsal-report` artifact，可核对源提交、源码树、镜像 ID、各步骤状态、恢复表记录数和文件校验结果。任何失败都阻断 aggregate validate。模拟 Docker 的脚本测试不等于真实容器运行通过。

此演练仅允许 GitHub Actions 的一次性环境，不能把 CI 标志加到生产服务器后运行。临时数据库、归档、凭据和完整容器日志不作为 artifact 发布。

## 集成和部署边界

- 保留现有审查栈的提交历史；通过精确 head 验证后，再固定独立的 `release/controlled-trial-*` 分支作为试运行基线。
- 主分支推送可能触发镜像发布和服务器部署。创建试运行分支与 Draft PR 不代表已合并或已部署。
- CI 的 MinIO 源码构建仅用于测试；生产分发问题 #35 仍需可访问、经过版本治理的生产镜像。不能把这份旧版 CI 镜像直接发布为生产方案。
- 当前恢复演练使用合成数据，证明的是当前镜像及数据库/对象文件恢复链路；真实目标的 TLS、异地备份、恢复时长与业务签字仍须独立验证。
- 已有数据库的切换必须先停止写入并排空旧事件消费者，尤其是 #41 会计事件来源字段变更。不能在旧消费者运行时直接迁移，再用新版本重放历史事件。
- 回退应同时固定应用镜像、Compose/脚本版本、数据库兼容性与备份。仅切换旧 image tag 不能证明数据库可回退。

## 实际环境接入所需信息

目标环境地址与现有访问方式、部署开关及环境保护状态、生产对象存储镜像/服务选择，以及负责验收的业务角色。未能通过当前工具读取 GitHub Secrets/Variables，不等于这些配置不存在；不得为了验证其存在而打印凭据或触发部署。

接入之后应先在隔离试运行目标验证当前固定版本，再按业务清单验收采购、销售、库存、制造、工程文档和财务边界。生产切换需保留停写、备份、恢复与回退记录。
