## 产品与实现边界

- 交付检查按物料汇总需求和库存流水，不编造订单行的已交付数量，也不把同一份库存或未完成工单重复分配给多行。
- 库存数量观察不是预留，不构成交期或可发货承诺；未完成工单包括未开工工单。数据缺失或无法确定归属时显示未知／需核对，不显示假零或绿色通过。
- 业务状态与数量证据分开；没有新增“必须先生产才能发货”的规则，也没有把缺口自动变成采购动作。
- 默认销售发货整单原子提交；显式 `allowPartial` 保留逐行成功／跳过语义。事务重试只重试已回滚的冲突，提交后的事件派发失败不能重新执行出库。
- 原因弹窗保留准确的接口和权限。报工冲销失败后，安全重试保持同一原因和幂等键，不因重新打开弹窗而换键重发。
- 前端、只读模型、库存写入和记账分开实施与审查；不通过堆叠页面或迁移框架替代业务完整性。

## 后续集成项的验证要求

物料名称／编码／单位、订单列表与详情消费者、切换订单后的旧请求防护，以及三个订单 Chromium 用例，应在同一集成树验证；不能把后端证据 PR 当成界面已经修复。

逐流水记账修复由 issue #37 / PR #41 跟踪，上表已记录迁移、并发重复投递、事务失败重试、成本来源、租户隔离和小连接池场景的真实 PostgreSQL 证据。生产切换仍必须先排空并停止旧版消费者，不能让旧版无流水标识的写入与新版并行。历史凭证不能凭订单号推测归属并自动补写。详见 `plans/STOCK_EVENT_ACCOUNTING_IDEMPOTENCY.md`。

## 仍然不能宣称生产成熟

1. **历史冲销的原始出库身份**：现有退货行关联反向库存流水，缺少原始 outbound identity。逐物料净量核对不等于已经证明历史库位／批次的精确归属。详见 `sales-shipment-quantity-safety.md`。
2. **生产镜像与环境**：issue #35 的生产 MinIO 镜像分发问题未由 CI 源码构建解决；生产 Compose 没有被悄悄替换。TLS、密钥、隔离备份、目标版本恢复演练仍依赖真实目标环境。
3. **财务与业务签字**：部分开票、额度、期初余额及真实生产业务验收不能由测试夹具替代；也没有自动补跑历史事件或历史财务凭证。
4. **完整制造与移动端验收**：库存贸易 HTTP 流程不是完整按单制造验收；移动端打包不等于真实设备扫码、弱网和业务角色验收。
