# OneERP 公司内部 ERP 下一阶段计划

> 审计日期：2026-07-10  
> 审计分支：`refactor/remaining-tasks`  
> 审计提交：`0d09d9a610a1287cb5b01f6023050907f091c0d7`  
> 目标：形成“客户咨询 -> 报价 -> 合同/订单 -> 设计图纸 -> 原料采购 -> 加工生产 -> 入库/出库/发货 -> 收付款与总账”的可审计业务闭环。

## 1. 当前结论

OneERP 已经是一个真实可运行的 ERP 技术与交易内核，不是页面原型。订单、采购、生产、库存、应收应付、总账、工作流、权限、审计、AI 配置和部署门禁均有真实代码与测试。

但按本公司的目标业务链衡量，目前更适合“受控业务试运行准备”，不适合直接宣称完整可用或生产就绪。工程估算完成度约为 **55%~60%**。这个比例是按业务闭环加权后的审计判断，不是测试覆盖率。

当前最完整的是采购、库存、销售订单和基础财务；主要断点是：

- 没有客户咨询、销售线索/商机、正式报价及报价版本。
- 没有合同实体、合同版本、审批、签署和订单转化关系。
- 文件后端能上传到 MinIO，但图纸没有业务对象关联、版本、审批、发布和变更控制；Web 图纸页也没有调用上传接口。
- 生产具备 BOM、工单、缺料分析、自动采购和报工，但缺少工艺路线、工序/工作中心、质量检验和在制品控制。
- 报工记录与原料扣减/成品入库不在同一事务边界，库存过账失败时可能留下已成功的报工与工单进度。
- 销售发货能扣库存，但没有独立的发货单/送货单/装箱单业务实体。
- 财务已有应收、应付、收付款、贷项、退款、银行对账和财务报表，但“全部资金管理”仍缺少预收预付、费用付款、付款审批、资金账户/日资金视图以及可能需要的多币种。
- Docker Compose 配置可解析；2026-07-10 已在 2 GB 远程 UAT 主机启动五个服务并通过现有 9 步业务验收。该结果仍不等于生产就绪：恢复演练、HTTPS/公网入口、正式 GHCR 镜像和真实业务数据签字尚未完成。

## 5. 立即阻断项

以下问题应先于继续堆页面处理：

1. **生产报工与库存过账原子性**  
   `submitWorkReport` 先提交 WorkReport/WorkOrder，再调用库存服务。库存失败时业务状态可能不一致。下一阶段必须先做失败复现测试，再决定同库事务编排或 outbox/saga，不允许直接搬代码。

2. **图纸不是受控工程文档**  
   `FileRecord` 只有文件元数据，没有关联订单/产品/BOM/工单，也没有版本、校审和发布状态。现有 Web 页面是通用记录页，未调用 `/files/upload`。

3. **移动端不能进入生产**  
   当前 UI 预填 `admin/admin`，access token 存 AsyncStorage，只有出库申请流程；必须单独加固。移动端 moderate 依赖告警也应随 Expo 升级处理。

4. **税码兜底仍是 13%**  
   TaxCode 已实现，但未配置默认税码时仍会按 13% 兜底并写 warning。真实财务试运行应改为初始化阶段强制配置并在生产拒绝静默兜底。

5. **发布主线不可信**  
   当前真实能力在大型 Draft PR 中，GitHub `main` 仍不能代表本分支。下一阶段开发必须保持小批次提交，并尽快确定 PR #15 的审查/合并或 RC 切分策略，避免继续无限叠加。

## 6. 下一阶段实施顺序

### Phase 0：冻结基线并收口 PR

目标：建立唯一可信开发基线。

- 保持当前提交不再混入新业务功能。
- 清理或决定是否提交 `.graphifyignore`。
- 修正文档中已经过时的事实，例如“仍有金额 Float”；当前 Prisma schema 的业务金额字段已是 Decimal。
- 2 GB UAT 主机已完成容器启动和 `business-acceptance`；继续使用正式分支镜像重跑 `deploy-check`、`prod-smoke`、`staff-permission-smoke` 和 `restore-drill`，保留精确 commit 与报告。
- 审查并合并 PR #15，或由它切出一个经过验证的 release-candidate 基线。不要继续让 PR 扩大。

完成定义：确定一个精确 commit，CI、容器、恢复和现有 9 步业务验收均有报告；`main` 或明确的 RC 分支成为唯一基线。

### Phase 1：业务语义确认，不编码

目标：把公司真实单据和状态说清楚。

当前确认稿：[`PHASE_1_BUSINESS_SEMANTICS.md`](./PHASE_1_BUSINESS_SEMANTICS.md)。D1-D7 已确认，但仍不直接授权修改 Prisma；必须先完成汇率源、岗位成员、编号规则、审批阈值和技术边界评审。

已确认的业务方向：

- 售前首期采用一层客户需求单；报价支持多版本、多币种，不设置报价审批。
- 合同采用结构化台账和签署件，合同与订单一对多。
- 图纸设计、校审、批准三权分离，工单固定已发布版本。
- 生产按混合模式设计，首条验收链走 MTO，并纳入工序、外协和质检。
- 缺料先展示采购确认预览，由采购员确认后直接生成采购订单，不新增采购申请。
- 资金首期纳入预收预付、报销、借还款、备用金、账户调拨和多币种。

完成定义：形成业务词汇表、单据状态图、角色矩阵、编号规则和 10~15 条端到端验收场景。未确认的字段和状态不得进入 Prisma。

### Phase 2：售前到订单纵向切片

目标：先打通一条最小真实售前链，而不是一次做完整 CRM。

技术边界评审稿：[`PHASE_2_PRESALES_VERTICAL_SLICE.md`](./PHASE_2_PRESALES_VERTICAL_SLICE.md)。该文件明确不可变快照、幂等转单、权限、事务/事件和 migration 门禁；门禁确认前不创建 Prisma migration。

建议最小切片：客户需求 -> 报价 V1/V2 -> 报价发出/接受 -> 合同登记/附件 -> 转销售订单。

- 新模型和命名以 Phase 1 的确认结果为准。
- 复用 Partner、Workflow、Audit、Files 和现有 Orders facade。
- 每次转化保留来源 ID、版本快照和操作人，不能只复制当前值。
- Web 做一个销售工作台，统一查看咨询、报价、合同和订单，而不是四个孤立 CRUD 页。
- 加 API 集成测试和一条浏览器 E2E。

完成定义：业务人员能从一次咨询生成报价版本、发出并记录客户接受、登记合同、生成订单，并在订单时间线追溯全部来源。

### Phase 3：工程图纸与变更控制

目标：让“按客户需求设计图纸”成为受控流程。

- 为工程文档增加业务关联、版本、状态、校审/批准、checksum 和发布记录。
- 支持关联客户需求、报价、合同、订单、产品、BOM 和工单。
- 已发布版本不可覆盖；变更必须生成新版本或工程变更单。
- 实现真正的上传/预览/下载 UI，复用现有 `/files` 安全校验和 MinIO。
- 工单创建时固定使用的 BOM/图纸版本，避免后续修改污染在制订单。

完成定义：从订单能看到当前有效图纸；生产工单能证明使用了哪个已批准版本；旧版本仍可审计但不可误用。

### Phase 4：生产一致性与现场执行

目标：先保证账实一致，再扩展高级制造。

- 先为“报工成功但库存失败”增加红灯测试并修复事务/补偿边界。
- 增加工单幂等报工键，防重复提交造成重复入库。
- 明确并实现领料、退料、报废、良品入库和冲销单据。
- 按业务需要增加 Routing/Operation/WorkCenter；若实际生产很简单，可暂不建复杂 APS。
- 增加质量检验和不合格品处理的最小闭环。
- 扩展验收脚本：订单 -> 工单 -> 缺料 -> 采购 -> 收货 -> 领料 -> 报工 -> 成品入库。

完成定义：任何一步失败都不会产生无法解释的工单进度、库存数量或成本；重复请求不会重复过账。

### Phase 5：采购、发货和资金单据补齐

目标：补齐公司实际需要的控制单据，而不是重写已可用的采购/财务内核。

- 采购：增加缺料采购确认预览和幂等转单；询价/比价按配置可选，不新增采购申请；复用现有 PO、收货、发票和付款。
- 发货：增加发货单/送货单、装箱、部分发货、签收和冲销；库存流水继续作为账实底层。
- 资金：增加预收预付、费用/其他收支、付款审批和资金账户视图；多币种仅在业务确认需要时实施。
- 所有过账动作显示影响预览、二次确认、凭证/库存结果和失败恢复说明。

完成定义：采购和销售两条资金链都能从源单追到银行流水与总账凭证，并能执行业务冲销而不是删历史。

### Phase 6：全链路 UAT 与受控试运行

目标：用接近真实的数据证明系统能持续工作。

- 将 `business-acceptance` 扩展为完整目标链，至少覆盖报价版本、合同、图纸批准、生产、采购、库存、发货、收付款、银行对账和总账。
- 增加关键 Web E2E、权限拒绝、并发/重复提交、事件失败重放和备份恢复测试。
- 修复影响用户流程的 Hook warning 和错误状态；补 loading/empty/error/retry 一致体验。
- 移动端只在完成安全会话、生产 API 对齐和现场测试后进入试运行。
- 选择一个小范围真实订单试运行，冻结 schema，记录风险、责任人和回滚点。

完成定义：所有 P0 验收通过，恢复演练小于 1 小时，真实业务负责人签字，才可从“受控试运行”升级为“生产使用”。

## 7. 每批工程纪律

- 每个批次只做一个纵向业务结果，不混入 enum、框架升级或大 Service 拆分。
- 先用 `graphify query/path/explain` 和 `rg` 查调用关系，再改接口。
- 新业务先写失败场景和集成测试；涉及库存/财务必须包含幂等、事务、回滚和审计。
- 复用现有 Partner、Workflow、Audit、EventQueue、Files、Orders、Purchase、Inventory 和 Finance 能力。
- Prisma migration 必须有脏数据扫描、生产备份和回滚/前滚策略。
- 每批最少通过相关测试；合并前必须通过 `npm run validate`、安全审计和 Compose 检查。
- 任何真实 API key、管理员密码和生产 `.env` 不进入仓库、日志、截图或测试快照。
- Bun 作为后期独立优化项：先评估用 Bun 工具容器运行 smoke/acceptance 脚本；生产 API/Web 继续使用 Node.js。未经兼容性、Prisma migration、镜像和全链路回归验证，不整体切换运行时。
